# Datoko

A private Shopee dashboard built with Next.js, TypeScript, PostgreSQL, Prisma, Better Auth, and a PostgreSQL-backed background worker.

This is the first implementation slice: the application shell, owner login, Shopee authorization/callback, encrypted rotating tokens, durable order imports, and historical SKU cost snapshots. Local build, database, owner-session, and demo-browser checks pass. Real Google/Shopee consent and production deployment still require verification.

## Current status

Implemented:

- Responsive overview, order list/detail, product-cost editor, returns placeholder, connection setup, and sync history.
- Explicit read-only demo mode. It uses sample records and cannot authorize a shop or write live data.
- Email/password owner signup and login with hashed passwords and backend access checks. Google remains an optional authentication mode.
- Shopee authorization using a full-page form redirect, session/browser/nonce validation, one-use code claiming, clean callback redirects, and encrypted token storage.
- Atomic connection persistence and initial job enqueue via pg-boss's Prisma transaction adapter.
- Serialized rotating-token refreshes, connection generations, and reconnect/disconnect fencing.
- Updated-order polling, paginated detail reads, window checkpoints, bounded retries, and manual sync deduplication.
- Immutable checkout/cost snapshots; new cost versions apply to future sales.
- Exact decimal financial-delta logic and dependency-free tests for the late-refund example.
- Advertisement comparison with exact decimal ROAS, private normalized report imports, item-level adjustments, revision history, and explicit source-coverage checks. See [advertising documentation](docs/ADVERTISEMENT.md).

The Advertisement implementation and current verification results are recorded in [ADVERTISEMENT_TEST_REPORT.md](docs/ADVERTISEMENT_TEST_REPORT.md).

## Local development

Use Node 24 and PostgreSQL 17. The supplied Docker Compose file is optional; an existing PostgreSQL database also works.

```powershell
npm ci
Copy-Item .env.example .env
npm run dev
```

Open http://localhost:3000. Demo mode works without login/Shopee credentials. The development server binds only to localhost.

The lockfile records the successfully installed dependency versions. Development and build use Webpack. Windows builds serialize prerendering and disable the separate Webpack compilation worker following filesystem permission failures observed during testing. Before live use, start PostgreSQL (optionally `docker compose up -d`), configure its URL, and apply migrations with `npm run db:deploy`.

Repeat the local checks:

```powershell
npm run db:generate
npx prisma validate
npm run typecheck
npm test
npm run build
```

The initial migration was applied successfully to PostgreSQL 17.10. A database-to-schema comparison found no differences. See docs/TEST_REPORT.md for the tested environment and remaining live checks.

## Owner sign-in

Run npm run secrets and copy the generated values into the private .env. Do not paste secrets into issues, commits, or screenshots.

Email/password is the default. Start PostgreSQL and run `npm run db:deploy`, then configure the following in your private `.env`:

```env
DATOKO_MODE=live
AUTH_METHOD=email-password
EMAIL_SIGNUP_ENABLED=true
APP_BASE_URL=http://localhost:3000
BETTER_AUTH_URL=http://localhost:3000
DATABASE_URL=postgresql://datoko:datoko_local@localhost:5432/datoko
BETTER_AUTH_SECRET=<generated by npm run secrets>
OWNER_EMAIL=<your email address>
```

Restart `npm run dev`, open `/signup`, and create your account using the exact `OWNER_EMAIL` and a password of 12–128 characters. Signup signs you in automatically. Password hashes and sessions are saved in PostgreSQL; passwords are never stored in plaintext. No Google or Shopee credentials are required to sign in. The existing account schema supports password login, so no additional migration is needed.

This remains one private owner workspace, not a public multi-user service. Other email addresses are rejected by the server. Create the owner account locally before exposing signup on a public URL: this basic flow does not verify email ownership or send password-reset emails. After signup, set `EMAIL_SIGNUP_ENABLED=false` and restart to close registration; existing sign-in still works. Login/signup have per-process rate limits; use shared rate-limit storage before scaling to multiple instances.

To use Google instead, set `AUTH_METHOD=google` and configure `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. Google mode still requires a verified owner email. Register the Google redirect:

    http://localhost:3000/api/auth/callback/google

Use the production HTTPS origin for production. OWNER_GOOGLE_SUB optionally pins the exact Google account subject after it has been established.

## Shopee console setup

Use a sandbox partner app first. Configure SHOPEE_PARTNER_ID, SHOPEE_PARTNER_KEY, SHOPEE_ALLOWED_SHOP_IDS, TOKEN_ENCRYPTION_KEY, and SHOPEE_REDIRECT_URI. Sandbox and production credentials must not be mixed.

The Shopee redirect path is:

    /api/integrations/shopee/callback

For a hosted staging environment, register a stable HTTPS origin with Shopee. Do not assume Shopee accepts localhost. `APP_BASE_URL`, `BETTER_AUTH_URL`, and `SHOPEE_REDIRECT_URI` must use the same origin; sign in to Datoko through that origin before connecting so its session and authorization cookie return to the right host.

Sandbox V2 uses `https://openplatform.sandbox.test-stable.shopee.sg` for signed API requests and `https://open.sandbox.test-stable.shopee.com/auth` for seller authorization. The authorization URL sends `partner_id`, `auth_type=seller`, `redirect_uri`, `response_type=code`, and an unpredictable `state`. The callback validates the echoed state against the saved attempt and an HttpOnly browser cookie. Use the app's Test Partner ID/Test Key for API access and the sandbox shop's account/password only on Shopee's authorization page.

Keep `DATOKO_MODE=live` to enable database-backed operations and set `SHOPEE_ENV=sandbox` to select Shopee test services. `live` in the Datoko mode setting does not select Shopee production. Create test orders through the console's Test Order tool, authorize the test shop from Settings > Connections, and run `npm run worker` to import them.

Connect uses a native form POST followed by a 303 redirect, so the browser actually navigates to Shopee. After consent, the callback validates the initiating owner session, expected shop, environment, nonce, expiry, and single-use attempt before exchanging the code. It then verifies the token-scoped shop identity, persists encrypted tokens with a durable import job, and redirects to settings with no code/token in the final URL.

Sandbox connections can be tested while `SHOPEE_CALLBACK_QUERY_VERIFIED=false`. Missing, repeated, or ambiguous state fails closed; there is no cookie-only fallback. The legacy production adapter still nests `auth_state` in its callback query and remains disabled until the flag is true. That production path requires its own real provider validation; a successful Sandbox V2 state echo does not validate legacy query preservation.

Still verify in the authenticated console:

1. App type, Indonesian local-shop permissions, and exact sandbox/production regional hosts.
2. Callback registration matching and query preservation.
3. Order-list/detail optional fields, maximum date windows, history access, and rate limits.
4. Return and settlement scopes, schemas, and authoritative refund/fee identities.

The current conservative order window is seven days; history access defaults to 30 days and must be checked against the app's real limits. Initial coverage leaves a one-hour buffer from the moving history boundary so normal first-page retries do not immediately become coverage gaps. Actual coverage is stored and displayed. Limits are configuration, not a promise of available history.

Do not log callback queries or signed Shopee request URLs in reverse proxies or observability tools. They can contain short-lived authorization codes/access tokens. Application errors expose only controlled error codes.

## Worker and sync behavior

Start the worker separately after live configuration is ready:

```powershell
npm run worker
```

It uses the same database as the website. Every minute it checks which shops are due; it calls Shopee for orders every SYNC_INTERVAL_MINUTES, not every second. Manual sync queues work immediately. The website displays SQL records and refreshes its view independently.

For each order window, the worker uses update_time, a five-minute overlap, and a fixed upper bound one minute behind its clock. All pages and detail reads must save successfully before the checkpoint advances. A failed page leaves the checkpoint unchanged. Source timestamps and SQL uniqueness prevent stale/duplicate business records. Missing or ambiguous source fields fail visibly rather than becoming fabricated zero-value records.

The queue retries with bounded exponential backoff. An unresolved resource error stops further automatic enqueues until an explicit retry or successful queued retry clears it. A gap outside the configured queryable history is surfaced as HISTORY_COVERAGE_GAP. The worker never silently skips it.

Tokens refresh under a per-shop lock and save the access/refresh pair together. Reconnect increments a generation; old jobs cannot overwrite new credentials or advance checkpoints. An uncertain refresh exchange can require reconnection because a rotating refresh token may already have been consumed.

## Tests

Core tests need Node and the installed project dependencies:

```powershell
npm test
```

Database tests require installed dependencies and a dedicated migrated database whose name includes test. They exercise SQL durability, real Better Auth session enforcement, and the connect/import/retry/refresh/reconnect/disconnect service lifecycle using simulated Shopee responses. Never point them at the shop database.

```powershell
$env:TEST_DATABASE_URL = 'postgresql://datoko:datoko_local@localhost:5432/datoko_test'
$env:DATABASE_URL = $env:TEST_DATABASE_URL
npm run db:deploy
npm run test:db
```

The PostgreSQL service must already contain that test database. The CI workflow supplies a dedicated one. Run desktop/mobile browser checks against the production demo build:

```powershell
npm run build
npx playwright install chromium
npm run test:e2e
```

Browser tests use a fresh local server on port 3100; owner-authenticated browser tests use port 3101 and the dedicated TEST_DATABASE_URL. The test runner closes its server through IPC to avoid Windows process-tree shutdown problems. These suites do not prove real Shopee redirect compatibility. See docs/SANDBOX_TESTING.md for the console verification cycle.

`npm run test:auth` tests the production build over local HTTPS, including secure session cookies. It requires OpenSSL to generate an ephemeral localhost certificate (Git for Windows supplies a native copy); use `DATOKO_TEST_OPENSSL` to select another executable. Certificate verification is relaxed only inside this isolated browser test configuration. The temporary key and certificate are removed after the run.

## Deployment

For Vercel with Supabase, use `DATOKO_MODE=live` and `SHOPEE_ENV=sandbox` to test against Shopee's sandbox with database-backed records. Set the hosted HTTPS origin in `APP_BASE_URL`, `BETTER_AUTH_URL`, and `SHOPEE_REDIRECT_URI`. Use the Supabase session pooler for the current queue and advisory-lock implementation, and supply the public root-certificate PEM as `DATABASE_SSL_CA` from Supabase Database > Settings. The web and queue clients validate the certificate and hostname. `/api/health` checks access to an application table in live mode and returns 503 when the database is unavailable.

For a restricted database login, provision a private `pgboss` schema owned by that login during database setup. Queue startup reuses the existing schema and initializes its tables without requiring database-wide schema creation privileges. Prisma migrations cover the application tables; pg-boss maintains its own queue schema and version.

For hosted sync on Vercel and Supabase, set a random `SYNC_WORKER_SECRET` in Vercel production and the matching `datoko_sync_worker_secret` in Supabase Vault, then run [docs/worker-schedule.sql](docs/worker-schedule.sql) as the database administrator. Supabase Cron invokes the protected `POST /api/internal/sync` endpoint every minute. It refreshes tokens, queues shops when their configured sync interval is due, and processes one queued job per invocation. Overlapping invocations use a database lock. Long imports retain their remaining windows and page cursor in the durable queue; only completed windows advance their checkpoints. The endpoint returns counts and controlled error codes, never tokens or order records.

Alternatively, run the persistent worker separately with `npm run worker:production`. Deploying the Next.js website alone does not start this process. Both worker modes share dispatch, token refresh, checkpoints, and idempotent order imports.

Deploy the same repository as a web service, a persistent worker service, and PostgreSQL. Railway commands:

- Build: npm run build
- Release migration: npm run db:deploy
- Web start: npm start
- Worker start: npm run worker:production
- Health check: /api/health

Supply secrets separately for each environment. Keep production callbacks on HTTPS. The worker needs a direct PostgreSQL connection for session advisory locks. Configure backups, recoverable encryption-key storage, and worker monitoring before relying on it as the permanent business record.
